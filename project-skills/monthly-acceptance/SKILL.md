# 月度大盘数据验收

**从结果推查原因：类目结果 → 变化贡献 → 影响排序 → 解释与反证 → 源数据 → 使用结论。** 全量重推后重新观察全部历史；SQL 负责可靠计算，模型选择假设、下钻深度和报告表达。先定位改变了业务判断的部分，避免把小噪声写成主要问题。

人工理解或微调时打开 [可视化说明](references/acceptance-guide.html)，执行时不必加载。方法版本 2.1；项目事实与历史裁决分别保存。

## 口径与边界

- **国家 × 公司标准类目 × 月份**是主要观察切片；中国合并淘宝、天猫。商品单位是 **SPU/product_id**，Amazon 对应 parent_asin；SKU 只用于必要的原始规格、父子归属和价格核查。
- 核心结果是**类目 SPU 数量、SPU 价格带、销量、销售额总量**。销量既是独立结果和排序依据，也用于量价解释；平均价格不替代价格带分布。四个结果的影响分别评估，不用低销售额直接豁免销量、数量或价格带失真。
- 主分析用 `monthly_sales_with_dim` 的公司 std 视角，回溯 `monthly_sales_wide_new` 的平台原始类目与细行；with_dim 是代理，不等于最终治理发布面。原始行/映射有重复或冲突时先核对，不把重复求和当有效结果。平台采集范围完整性单独守门。
- 治理取证用 Doris，只执行 SELECT/SHOW/DESC/EXPLAIN，表引用三段式。数据估算不等于实际成交额，缺少观测不等于零。不同国家本币金额不直接相加。报告与反馈仅落盘。

## 一条完整的工作流

### 1. 固定本次观察边界

读 `验收/config.yaml` 和 `验收/项目范围.md`；交接文件重点用于核对原始平台类目范围。运行 `python3 .claude/skills/monthly-acceptance/scripts/acceptance_run.py start --month YYYY-MM` 建立唯一运行包，冻结方法与配置；按包内 inputs 版本取证。输出路径由脚本返回。

先检查新月到货、应有历史月份、明显推丢/推薄，已到货部分继续。可以使用既往**数值快照**辅助完整性核对，但不前置读取旧报告、案例和原因判断。以项目预期范围判断缺失，不能因为上次也缺就当正常；普通历史数值变动本身不是问题。

记录本次上游批次/更新时间（可取得时）、查询时间及国家各月关键指纹，收尾按同口径复核。若期间重推或指纹变化，重新取得受影响证据，不能混合批次形成结论；无法固定批次时披露一致性验证的限度，指纹相同不等于事务快照。

### 2. 看类目结果，并守住范围完整性

按国家查看总量，再逐层查看公司 std 类目，全部历史都覆盖到。比较 SPU 数量、价格带中的商品数/销售额组成、销量、销售额及其增减；品牌结构作为类目结果的细分视角，必要时独立看重点品牌，避免总量抵消掩盖问题。记录实际检查范围及分页/截断，不以只看头部候选冒充全量扫描。

同时检查平台约定范围和公司 std 的首次观测、中途缺失、截至本次窗口仍未恢复，以及约定但全期无记录。标明类目轴、完整路径和有效时期；改名、迁移、补采或映射变化需核对，不能直接叫市场新增/消失。范围漏采即使暂时金额低也不能因未映射到 std 而漏掉。

### 3. 找到谁改变了结果，先排影响

对异常结果将销量和销售额增减逐层分解到**不重叠的细分类目、品牌或 SPU**，沿同一父类目追踪。分别看增减件数/金额、占对应类目净增减的贡献、对对应类目增长的百分点贡献，同时检查 SPU 数量和价格带影响。量增价跌、量跌价涨可能抵消金额，销量变化不能被金额平稳掩盖。净变化接近零时看正负抵消与绝对变动，不能被不稳定的贡献百分比误导。

局部变化解释了类目销量或销售额的大部分涨跌、改变趋势方向或主要价格带时，提前排查。头部按类目内 **SPU 销售额及累计贡献**识别，选择足以覆盖主要组成的集合，不固定 Top100/1000；兼顾前后期头部和销量/金额变化贡献大的商品，不能遗漏消失的旧头部。

**轻量检查尾部影响，按影响停止。** 若尾部对四项结果均无实质影响，合并为风险提示，不逐条深挖或列成重点问题。若商品群使销量、SPU 数或价格带明显失真，或尾部累计金额已改变类目结论，则重新提升优先级。不是在计算总量时删除尾部。

### 4. 带着问题解释与反证，直到源数据

先做原始身份、重复、映射及量价的轻量一致性检查，避免给明显计算错误寻找市场故事；此后市场假设与源数据核验往返推进，顺序由证据决定。

从主要贡献商品的结果提出问题，核对真实折扣、品牌活动、准确地区日历与季节，允许提前/滞后起量。进一步采用**开放的外部市场分析框架**：按本次国家、时期、类目和变化结构，自由提出、修订有关需求、使用场景、供给、购买行为或交易方式的假设。外部驱动包括突发事件和逐渐形成的趋势；示例只帮助理解，不构成固定分类或必查清单。

沿“外部变化 → 行为/供给/交易结构变化 → 相关类目与 SPU → 四项结果”检验传导，按假设选取对应时期的权威证据和反证，见 `references/methodology.md` 与 `references/cross-validation.md`。区分整体需求变化、渠道交易迁移与采集/映射变化，它们可以叠加；被采平台增长不能直接代表全行业增长。价格带变化仍需区分同 SPU 变价与商品/销量结构迁移。

趋势合理性与具体幅度是否得到解释分别判断，不编造无法识别的影响倍数。重要且仍明显不合理的部分继续溯源；确认数据问题后按四项结果影响写入最终审计报告，证据不足保留待核，按判断需要收敛外部研究。

根据证据继续核对父子归属、品牌/类目迁移、源数据缺失、抓价、量价关系、重复及映射放大、拟合变化等。贡献分解只定位变化，不证明数据错误；固定 SPU 上涨、尾部变化或偏离节日形状均不能单独确定原因。查看原始细行时保留商品、国家、月份与路径，使发现可以复核。

内部本品数据可用时对齐口径，优先比销量，并看金额对当前类目结果的影响；缺数据如实说明，相符也不自动构成独立验证。Amazon 的具体节点、归属或商品趋势仍不清楚且外证能改变判断时，按 `references/cross-validation.md` 使用 Sorftime；不逐类目机械调用。

### 5. 按影响形成结论，独立归档

先在运行包保存 `观察.md`，形成自己的事实与假设，再按具体问题调取历史比较；历史问题本次重验后才能作为本次发现。保留实际查询、参数/范围和结果到 evidence；不复制旧数字充当新证据。

每次只交付**一篇自足的报告**：开头一段给出最精简的使用结论与优先处理方向；正文依次交代范围与历史完整性、四项结果、重点异常追因、最终使用判断。每个重点问题在同一处讲完整：**变化与影响 → 证据及反证 → 判断与理由 → 核查或修复方向**，说明证据为何促使下钻或停止。正常环节用一句有范围、有依据的话带过，不能折叠、隐藏或要求跳转；未查、无观察、待核与正常分清。默认不用表格，不生成图片，复杂分支按需用文内 Mermaid 逻辑树。原始明细留在证据包，读者不必打开它才能理解重要结论。写法见 `references/report-writing.md`。

交付前对照 `观察.md` 与 evidence 复核必要路径、四项结果、贡献、正常依据及推论边界，并从头通读：开头能否掌握重点，每个问题的证据能否支持判断，结尾能否据此行动。综合给出放行/有保留放行/打回及适用范围；具体核查请求写在对应问题结尾，不另拆必读反馈。

保存 `报告.md`；只有用户另要对外反馈稿时才生成 `反馈草稿.md`。运行 `acceptance_run.py seal <运行目录>` 封存证据包。**封存只检查文件与哈希，不代表报告完整或业务验收通过。** 封存后不覆盖；补查新建运行并注明关联。仅测试写法时另建试读目录，注明复用的证据与未重新查询，不冒充新一轮数据验收。Obsidian 只交付该篇正文，旧展示版归档，默认不另建摘要、专题笔记或图表附件。放行不自动重建治理层，使用前还需核对 release 是否对应已验收上游。

人工反馈先定位范围、计算、判断或表达层，改最少的有效规则，并用失败案例和合理反例复验；旧版本归档，有效方法精炼替换。独立复验使用仅加载有效口径和本次输入的新会话，换目录本身不能清除既有会话中的旧判断。
