# 一篇沿排查路径讲清判断的报告

面向业务读者回答：商品数、价格带、销量和销售额能否使用，哪些异常足以改变类目判断，证据支持什么处理方向。**外层沿分析框架展开，内层把一个问题讲到底。** 骨架见 `../assets/report-template.md`，不要求机械填写每个子标题。

## 单篇文章的顺序

开头一段直接给最精简的使用结论、重要问题及优先方向；运行编号和技术背景不占据开头。正文依次交代**范围与历史完整性 → 四项结果 → 重点异常追因 → 最终使用判断**。问题按影响排序，正常检查放在相应环节，用一句有范围、有关键依据的话带过；不折叠、不隐藏，不用“其余正常”替代。

每个重点异常在同一处串起：**看到了什么、为何重要 → 哪些证据支持或削弱哪些解释 → 为何继续下钻或停止 → 当前判断、使用影响和下一步**。标题尽量表达判断。涉及历史变化时，说明合理参照时期及优先核查的缺失/修复时期；不要只报断点。下一步要具体到对象、月份和能改变判断的证据，必要时说明修复后如何复验。证据不足可以限制结论，但不能用无排序的“可能原因”代替工作判断。查到源记录相同只证明上下游一致，尚未证明原始采集正确。

结尾明确放行、有保留放行或打回的适用范围，交代未闭合事项对业务使用的影响。具体供应商核查请求写在对应问题结尾；只有用户另要对外反馈稿时才单独生成。

## 文字与证据

- 默认不用表格，不生成图片。少量并列比较只有用文字难以讲清时才用小表格；不要把完整月序列、排名和字段清单搬进正文。关键数字紧贴它所支持的判断，读者不跳转也能理解论证。
- 复杂且容易混淆的判断分支按需用 **Obsidian 文内 Mermaid 逻辑树**，节点交代支持、反证或待核状态，正文仍写出结论；直线流程和几句话能说明的关系不用画树。不给正常环节另做图，也不堆提示框。
- 四项结果都要有交代，平均价不替代价格带。用改变判断的数值说明商品集合、量价抵消和头尾累计影响；对四项均无实质影响的尾部合并提示，金额低不能直接豁免数量、销量或价格带失真。
- 贡献就近注明国家、对应公司/平台父类目、比较月份、件数/本币金额及分母。净变化很小时说明正负抵消，不用失真的百分比排严重性。变化贡献、敏感性分析、已确认错误影响分清；排除疑似商品后的结果不称为真实市场。
- 实测事实、用户或供应商补充、我方推断分别说明；同一商品编号不自动证明产品身份未变。市场解释随问题给出传导、对应时期的证据与反证，不按事件类型填章节，不编造影响倍数。未查、无观察、待核、已解释和正常分清，缺输入的内部对拍不算通过。
- 引用贴近相关论据，仅供追溯；必要事实留在正文。查询、字段、完整商品清单、逐项校验与运行信息放证据包。必要的商品标识就近保留，不要求读者打开另一篇文章才能定位问题。

## 写完后的验收

对照本次观察与证据，复核范围/批次、全历史、四项结果、贡献与头尾、解释与源数据、内外部核验、使用限制是否都有着落；重点发现不能因总量抵消而遗漏，正常结论要有依据，缺口不能写成通过。按问题顺读，检查证据是否支撑当前判断，下一步是否能实质推进结案；数字准确也不能替代这项阅读检查。

每次只交付一篇完整正文，不另建必读摘要、专题笔记、数字备查或图表附件。证据继续独立归档；Obsidian 保留一份当前阅读入口，旧展示版归档后再更新。仅测试写法时注明沿用哪次数据与哪些新增材料，不把改写称为数据库重跑。封存只验证文件和哈希，不代表业务验收通过。
